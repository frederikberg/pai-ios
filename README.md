# PAI iOS

Native SwiftUI client for PAI Cloud — a personal system that runs Claude Code sessions on a cloud
VM and drives them from a phone. This app is the iPhone front end for it.

**This is not an app you can install and use.** It talks to one specific privately-hosted backend,
and that backend is not public. It is here because the parts underneath it are worth reading and
reusing, and because a public repository gets unmetered CI.

## What is worth taking from here

| | Where |
|---|---|
| A chat transcript that never jumps while loading older messages — `UICollectionView`, precomputed heights, prepend compensation in the layout rather than after a batch update | `PAIKit/Sources/PAIKit/Layout/`, `PAI/Transcript/` |
| A markdown editor over one plain `UITextView`, with syntax highlighting over the source rather than a live preview | `PAIKit/Sources/PAIKit/Editor/`, `PAI/Notes/Editor/` |
| Notes that work in flight mode: a cached index and notes, files kept under a size budget, and an outbox that holds every unsaved edit until the server has it, with conflicts settled without asking and nothing lost | `PAIKit/Sources/PAIKit/Stores/Notes/` |
| A markdown parser that decomposes into synchronously measurable blocks, on top of swift-markdown, with LaTeX typeset natively by SwiftMath so a formula's size is known before layout | `PAIKit/Sources/PAIKit/Markdown/`, `PAIKit/Sources/PAIKit/Layout/MathTypesetter.swift` |
| A debug bridge — an HTTP server inside the app, `#if DEBUG`, so CI can ask the app what it thinks instead of reading pixels off a screenshot | `PAIKit/Sources/PAIKit/Debug/` |
| Streaming over `URLSessionDataDelegate` rather than `URLSession.bytes(for:)`, so the transport compiles and tests on Linux | `PAIKit/Sources/PAIKit/Networking/` |
| Building and shipping an iOS app **without owning a Mac** — signing from Linux via the App Store Connect API, a hand-written project file, TestFlight from CI | `.github/workflows/`, `fastlane/`, `Tooling/` |

That last one is the least documented thing on the internet and the most annoying to work out, so
it is the part most likely to be useful to someone else.

## How it is arranged, and why

Almost everything lives in `PAIKit`, a local Swift package. **The package builds and tests on
Linux; the app target compiles only on macOS.** That split is the whole architecture: package code
is proven in seconds for free, app-target code is proven only when a macOS runner runs. So the
views are thin, and anything a unit test could catch lives in the package.

| Path | What |
|---|---|
| `PAIKit/` | the logic and its tests — where the code is |
| `PAI/` | app target: views, and the few things needing an Apple framework. A buildable folder, so new files need no project edit |
| `PAI.xcodeproj` | written by hand, small, not regenerated by any tool |
| `Config/` | xcconfig; `MARKETING_VERSION` comes from the git tag via CI |
| `Tooling/` | checks that catch macOS-only compile errors without a Mac; `sim/` is the simulator lane the `Mac` workflow runs, usable on any Mac |
| `fastlane/` | build, sign, upload — the same lanes locally and in CI |

## Signing in

The backend sits behind Zitadel. "Sign in" runs the authorization-code flow with PKCE in the system
browser sheet (`WebAuthenticationSession`, the shared browser session, so a login already made in
Safari is reused) against a native, public Zitadel application, and comes back through
`pai://oauth/callback`. The token set lands in the Keychain. When the backend refuses the access
token — a 401, or the proxy's plain-text 403 — the app refreshes it once, however many requests were
refused together, sends the request again, and signs out only when the refresh itself is refused.
`PAIKit/Sources/PAIKit/Auth/` holds the flow, the token endpoint and the renewal; the Keychain store
and the screen are in `PAI/Shell/`.

Signing in is the only way in: the app has no field for a pasted token, and a phone that still
holds one from an earlier version is asked to sign in. Every request carries the phone's name in
`X-Device-Name` (iOS reports the generic model name, such as "iPhone", unless the device name
entitlement is granted), so the backend's list of signed-in devices can show it. Signing out
first ends the phone's sign-in on the backend, which also drops its push token (best effort, a few
seconds at most),
then revokes the refresh token at Zitadel as well as clearing the phone, and the phone drops its
push registration so the next sign-in registers afresh, and a backend that revokes the
device from that list signs the app out the next time it asks (`401` with `device_revoked`), with
the message "This device was signed out".

## The share extension

`PAIShare/` is a second target: PAI in the system share sheet. One screen offers what the person has of three targets, Todo, Note and Session. **Todo** makes a new todo: shared text or a link is its words, photos and files become its files. **Note** makes a new note in the default notes folder: shared text is its body, a link a line of its own, photos and files are embedded at the bottom. **Session** sends everything through the same `POST /api/drafts/{key}/attachments` a composer's upload uses, onto an existing session's draft or the new-session draft, where it waits until a message is sent from it. A target that did not take everything keeps what was shared on screen and offers to try again, which sends only what is missing. The view holds only what needs an Apple framework; `ShareStore`, `ShareTodoStore` and `ShareNoteStore` in `PAIKit` hold the rest. The app copies its sign-in into a Keychain item in a shared access group, which the team wildcard in every provisioning profile already covers, so neither bundle id needs a capability or an App Group.

Signing needs one thing the app alone does not: the App Store profile `PAI Share App Store` for `com.frederikberg.pai.share`, in the repository secret `IOS_SHARE_PROVISIONING_PROFILE_BASE64`.

## The Control Center control

`PAIControls/` is a third target, a WidgetKit extension offering three 1x1 controls: Quick actions opens the quick-actions screen, Alarm opens the Alarm app and New todo opens the add sheet for a todo, from Control Center, the Lock Screen or the Action button. `SharedIntents/` holds the intents they run and is compiled into the app as well as the extension: a control opens the app only when the app holds the very same intent type.

Signing needs the App Store profile `PAI Controls App Store` for `com.frederikberg.pai.controls`, in the repository secret `IOS_CONTROLS_PROVISIONING_PROFILE_BASE64`.

## Alarm

The Alarm app (Apps, or the Alarm control) lists the armed alarms, pins ringing ones on top with Dismiss, and arms a new one, from the "+" or a tap on the empty area, either at a clock time (an hour and minute wheel) or in a number of hours, minutes and seconds from the moment of saving, with an optional name; an alarm whose time has seconds lists with them. The backend rings an alarm by sending a push every few seconds; tapping one opens the app and stops the alarm on every device. A stopped alarm's banners leave the notification list again: a background push removes them at once, and opening the app removes those of any alarm that is no longer ringing. The interval and the ring duration are settings of the person, edited inside the app. Settings also lists, creates and revokes the watch keys a Garmin watch signs in with; a new key is shown once.

The pushes are time-sensitive, so the app declares the Time Sensitive Notifications entitlement in `PAI/PAI.entitlements`. A build signed for TestFlight needs the capability enabled on the App ID and a provisioning profile created after that.

## Weather

The Weather app (Apps, or `pai://weather`) answers two questions in two rows: "Now" is the next hour from the rain radar (a chance, when rain reaches you, how close it is and whether it is closing in) and "Later" is the next twelve hours. The footer names the place, how old the location is and the data sources.

Where you are comes from one iPhone you choose: Settings, Location, "Use this iPhone for location". That phone asks for location access (while using the app first, then Always) and takes one fix each time the app comes to the front, plus significant-location-change monitoring (low power, moves of about 500 m). On the owner's phone, Always access also records visits (arrival and departure) and watches the named places the server lists (up to 20 geofences), so reminders at a place fire and a day's stays can be read back. Nothing runs continuous updates. Every point goes through an on-disk queue and is sent in batches, so a lost connection loses none; the server keeps the owner's history and only the latest position of anyone else. The two purpose strings live in `Config/Info.plist`; the `Mac` workflow asserts both survive into the built app.

## Apps and their order

The apps have one order, the person's `app_order` setting, shared with the web: a list of apps with a line in it. It is arranged in Settings, Appearance, App order, by dragging an app above or below the line. Three places draw from it:

- **The Apps list**, opened by the grid button in the top bar of every app's first screen, of the session list and of a session: the apps above the line first, the rest under More. Picking an app returns to the screens it was left on; picking Sessions returns to the session that was open.
- **The start screen**, where the app lands when it is opened with nothing else asked for (no link, no notification, no shortcut): the same apps as tiles, the session list one step back. An app opened from anywhere sits on the start screen, so Back from its first screen leads there.
- **Sleep mode's screen**: the same tiles without the apps sleep mode puts away.

## Quick Actions

Quick Actions is an app in that order, reached also from the Control Center control and the Action button. It is a grid of three columns and five rows; every tile has the same size and anything past the fifteenth is reached by scrolling. What is on it is the user's own: a long press on any tile, or Edit, opens the Actions Library, which lists every built-in Action and every Shortcut under Grid, More or Hidden. Grid and More are reordered by dragging, each row's menu moves it between the three, and the More tile opens the More list while it holds anything. A Shortcut is a name and a link another app opens (an app's own link, any web address), added and deleted in the Library. The arrangement is kept on the phone and not synced; a fresh install starts from a standard layout. One action is about the phone itself: **Pause push** asks for how long (30 min, 1 h, 3 h, until 07:00) and pauses push to this iPhone; while paused its tile says until when, and a tap resumes.

## Settings and sleep mode

Settings is a list of pages in two halves: what is yours (microphone and dictation, notifications, voices, appearance, location, devices and sign-ins, history, this iPhone) and, for the owner, Administration (system, alerts and routing, mail server, providers and keys, models, integrations, voice and sound, agents, people and devices, diagnostics). A guest has their own pages and none of Administration. A card in Yours says whether its settings are synced across devices or belong to this iPhone; an Administration card says "All users" only where a setting changes what guests get, and carries no tag otherwise. Notifications has the person's push and mail switches, this iPhone's push (on or off, paused for a while), and the other devices; Providers and Integrations list the outside services with a test each, and Models sets a default and a fallback model per feature. Most values are keys of the server's settings registry, drawn by one generic row from the schema the server serves, so a key the server adds appears with no change in the app; switches and choices save when changed, text, numbers and lists with their own Save button.

Sleep mode (Settings, Notifications, Sleep mode) is off until it is turned on with a window (22:00 to 05:00 to start from) and a PIN. Inside the window the session list is replaced by a screen of the other apps, drawn from the same list as the Apps sheet minus the apps that are about the agents, in the person's order; every way into a session (a tap, a link, a notification, a shortcut, an intent) ends on that screen; a dictation into a session is stopped and a call hung up as the window begins; the app badge and the arrival banners stay quiet. The phone tells the server its window on every registration, and the server holds back every push to it inside the window except alarms. Quick Actions keeps its layout, with the actions that start a session greyed under a moon. The PIN, kept as a salted digest on the phone, is asked for to wake early, to change the window or the PIN, and to turn the mode off. It keeps a decision from being undone on impulse; it is not security.

## Me

Me is a diary and a view of the day for the signed-in owner. The launcher's middle tile, "Me", opens a composer with the keyboard up: a face (heavy, okay, good), a few words, or both, an optional earlier time and a Private switch. Send always succeeds on the phone: the entry goes to a small outbox under its own id and is delivered when the network is there, so a retry never makes a second row. The draft survives closing the sheet. The composer has the same microphone as a session's: a tap starts the default dictation mode, a long press the other one, and the words land in the entry like typed ones. The diary draft is a device-only draft: it is kept on the phone and never sent to the draft routes.

The Me screen (Apps, owner only) has three views under a segmented control. Today shows where the day stands: a ribbon of the day on a 00:00 to 24:00 axis (sleep and activities, appointments, when the person wrote, tasks ticked, diary faces, a line for now), three lines of body figures, the write card, a read-only task card (appointments still ahead, open tasks in Todos' order (the Desk first, under its section names, then what else is due), ticked tasks with their times; a row opens the address the server gives for it, or nothing when it gives none) and the plan agreed for the day. 14 days is a grid with a column per day that prints its numbers (diary dots, the night as one bar from bed to waking, the time asleep, sleep score and battery on waking each as a line through the days over its numbers, activities, messages, agents running overnight) above a day detail with the same ribbon, fact lines and agent time per project. Diary lists entries as compact rows that open in place, with the counts of faces over the 14 days on screen, filters, search over the loaded pages, edit, make private, delete with undo. A blank cell means nothing was recorded; there are no scores, streaks or comparisons. The task list is read through the server and asked for on opening, on coming back to the screen and on the refresh icon, never on a timer.

## Camera Import

Camera Import (Apps) copies the photos and videos of a camera plugged in by USB-C into the photo library, so whatever backs up the library (the Immich app, iCloud) takes them from there. "Import from Camera" reads the folder picked last time; when there is none, or it no longer opens or lists nothing (a folder grant onto an external drive may not survive unplugging it), the folder picker opens instead. Any folder of the camera works, the volume root included: everything below it is read. "Choose Folder" picks another one. A camera with several USB modes has to be in its mass-storage one to show up in the picker (Insta360 Ace Pro: USB Mode → U-Disk Mode, where Files lists it as "Untitled" with the media in `DCIM/Camera01`).

JPEG, DNG, HEIC, MP4 and MOV files are imported, each as its own asset under its own file name; video proxies (`.lrv`), thumbnails (`.thm`) and everything else are skipped. Files are handed to Photos one at a time by file URL, so the camera's bytes and metadata arrive unchanged and memory stays flat for long videos; a file Photos cannot take where it lies is copied into the app's temporary folder first. The creation date is the one Photos reads from the file.

The app remembers every file it added, by name and size, in its own storage: add-only access to the library, the only permission it asks for, cannot read the library back. A second run adds only what is new, also after the imported files were deleted from the library once they were backed up; a file that failed is tried again, and "Stop" ends a run after the file in hand. The screen stays awake while a run is going; leaving the screen stops the run. The purpose string (`NSPhotoLibraryAddUsageDescription`) lives in `Config/Info.plist` and the `Mac` workflow asserts it.

## Todos

The todos live in PAI Cloud's Todos. The app holds the engine for them (`PAIKit/Sources/PAIKit/Stores/Todos/`): the open todos, the lists and the desk are kept on disk, so a cold start without a network still has them, and every change (add, tick, untick, the desk) is queued on disk and sent in order under its own change id, so a resend after a lost answer is a replay and never a second todo. Without a network a change waits; with an expired sign-in the whole queue waits for the next one; a change the server refuses is dropped with a toast, and the words of a refused add are kept.

Todos is an app of its own in the Apps list (and `pai://todos`). From the Apps list it opens on the view it was on last, and before any on the first favourite view, usually Today, with the desk above it; the bar on top names the view shown. The desk has three states: a bar with its count and first card, the desk over the list, or the desk alone. Today opens with the desk over the list and every other page with the bar, and each remembers its own state; a tap on the desk's own bar, anywhere that is not a control, folds it and opens it again as it was. Views, lists and tags open as pages from "Views and lists", with the same colours, symbols and counts as the web app, or by typing a few letters of their name into the switcher beside it (Return goes to the best match). Todos' settings (from the switcher or the bottom of Views and lists) hold the time zone, when the day starts, how early a deadline shows and where new todos go; the default nudges; each list's name, layout, look, lock and people, sharing included; each tag's name, colour and quiet, merging and deleting (tags on no open todo are listed first); and the views: a new one from a name and a query, renaming, the order (Edit, then drag), favourites and deleting, and what a todo added in the view starts with: a view without such defaults can take the ones the server reads from its query (`tag:home` gives the tag), offered after a save and by a button on the view's form. Scopes, a view's layout and grouping, and the keyboard shortcuts are on the web. The nearest horizon reads Next (stored as `now`): the desk is what is being done now. A row ticks from its circle or a swipe left, goes on the desk with a swipe right, and opens its subtasks from the chevron. The round button adds a todo with the page's defaults, which show as chips at once and are left off this todo with a tap; a field the line names replaces its default, and "no date" in the line leaves the page's day off. A word the line is read by (a day, a tag, a horizon) is marked in the line and listed under it, and stays so while typing goes on. The keyboard's Return key is Send: it adds the todo and keeps the line ready for the next one, as the round arrow does, and a strip on the keyboard has an @ key for tags. A line with a someday word is added as someday. The description is written in the sheet, under the line, and a picture pasted into the line or the description becomes a file of the todo. A file held for the new todo opens in the viewer with a tap. Taps under the line put the common words into it (Today, Tomorrow, @ Tag, Next, Desk, Deadline), and "Add and open" adds the todo and opens its sheet with every field. A long press on it also offers describing the todo in plain words: those go to the server's model, which reads them into one or several todos (days, tags, subtasks) sent as one change, and the first one opens. The words, typed or dictated with the app's own microphone, stay in the sheet while the model reads and when it fails, with the reason said, and can be added as typed. A tick, a drop, a skip, a delete, a desk clear and an add each answer with a toast whose Undo takes the change back, on the server or, when it has not left the phone yet, out of the queue. Tapping a row opens the todo's sheet (closed with Close), where every field can be changed: title, horizon, when (day, time, repeat and nudges: before the time, or whole days before the day or deadline at a time of day, the ones the person's default nudges made marked as such), deadline, tags, list, desk, subtasks (each opens its own sheet; added from a line read like the add sheet's, so `p1` or `#tag` there apply to the subtask) and the description, shown rendered and kept when its screen is left as when Save is tapped; its files, links and latest changes are shown too. Its menu moves it under another todo, found by search, or out to the top level. Upcoming and the Logbook are day screens. Upcoming opens on tomorrow; a scroll up shows today and the days behind that held something, done and dropped todos among them, and a row on top looks further back. A long press on a row offers Select: rows then carry a selection mark, and a bar on the bottom completes, puts on the desk, sets the day, horizon, tags or list of, or deletes everything selected, each as one change with one Undo; the Undo toast stands above the bar. Search uses the web app's search with the same words and query language (`tag:home`, `is:done`); it opens with the keyboard up, and before anything is typed it offers a short help with examples, what was opened from search lately and the searches run often, the same list the web app shows. The desk can be rearranged ("Arrange") and split into sections; a section's title moves alone, and a long press on it renames it, removes the title alone, or clears it with the cards under it. Every one of these is a change in the queue, so it works without a connection too. A change made elsewhere (the web app, another phone, an agent) shows in the open app at once: while the app is in front it keeps one request at the server's change feed open, which the server answers when something is written.

A todo can be added without opening the app:

- **Add Todo**, an App Intent with a text parameter, from Siri ("Add a todo in PAI"), Shortcuts or the Action button through a shortcut. It answers whether the todo was added or waits on the phone.
- **Describe Todo**, an App Intent that hands plain words to the server's model; without a network the words are queued as Add Todo would queue them.
- **Open Todos** (the view it was on last), **Open Todos View** (a view or list picked in Shortcuts) and **Open the Desk** (the Desk in full), App Intents in the Shortcuts app; Open Todos is also a Siri phrase.
- **Todos**, **New todo**, **Search todos**, **Go to** (the switcher), **Desk** and a tile for one chosen view or list, in the app's own Quick Actions.
- **New todo**, a Control Center control, and **New todo** and **Describe todo** in the app icon's quick actions, opening the add sheet with the keyboard up.
- **Todo** in the share sheet, for shared text, a link (attached to the todo), photos and files (the todo's files).

The words go to the server's capture parser (dates, `#tags`, `/List`, `*` for the desk), the same reading the web's quick add gets. Words captured without a network are read when they go out, unless the day has turned in between: then they become the title as they are. The share sheet has no storage in common with the app and keeps nothing: when the server does not take a shared todo within a few seconds, the sheet stays open with the words and a Try again. Add Todo through Siri or Shortcuts keeps a todo it could not send on the phone, and it goes out the next time PAI is open. A link to `/apps/todos` from another app opens Todos at the view, the list or the todo the address names (`/apps/todos/t/<number>`, `?t=<number>`), and tapping a nudge's notification opens its todo. A refused todo is told with its words, as a toast while the app is in front and as a notification otherwise; a server error is tried again a few times before it counts as refused.

## Notes offline

The notes open without a connection. The index, every note opened on the phone, the favourites,
each container's attachment list and every file viewed are kept on disk, so the list, the filter,
the "Find note" quick action and those notes and files work in flight mode. A note never opened
says it is not on the phone.

Editing the body, renaming and favouriting work offline. Every unsaved edit is written to disk
within a moment of typing and again before each save leaves, and stays there until the server has
it, so neither flight mode nor the app being killed loses one. Edits that waited go out when the
network is back, bodies before renames. If the note changed on the server meanwhile, the phone's
version is written over it and the version it replaced stays in the note's history; a toast says
so. An edit typed while online that the app could not save before it was killed is sent as an
ordinary save instead, so a change made elsewhere in between raises the conflict banner. Creating
and deleting notes, adding or changing files, full-text and semantic search, history, links, the
summary and sharing need a connection and say so.

Every save from the phone is recorded in the note's history as the phone's (`phone`, or `offline`
for an edit that waited), never as the web's, so a phone save and a burst of web saves each keep the
version they replace. A rename made on the web while the phone was offline still loses to a waiting
phone edit of a note linking to it: the link rewrite is in the history, the phone's text is what
stays.

An edit the server refuses (most often because the note was deleted elsewhere) is not sent again by
itself. The save badge in the editor and Settings → Notes offline offer to copy or discard its
text; the same list holds any saved edit a different version of the app wrote in a form this one
cannot read, which is set aside rather than overwritten.

Settings → Notes offline sets how much space this takes (5 GB by default), shows what is used,
and clears it. Only files are dropped to stay under the size, oldest first. Clearing never touches
edits that have not synced, and keeps those notes on the list.

## Building and checks

The package needs only a Swift 6.2 toolchain, on any platform:

```
swift build --package-path PAIKit --build-tests && \
  swift test --package-path PAIKit --skip-build
swift format lint --recursive --strict PAIKit PAI PAIShare PAIControls SharedIntents
```

Two scans cover the app target without an iOS SDK: `./Tooling/parse-swift.sh` checks syntax (it stops
before name resolution), and `./Tooling/swift6-lint.py` flags the few Swift 6 constructs that compile
on Linux and fail on a Mac.

The app target needs Xcode. CI builds it on a macOS runner; there is no way around that, and no
attempt here to pretend otherwise.

## CI

Checks run on pull requests only; `main` runs nothing, and the `Validation` job of `Free checks` is
the required gate.

| Workflow | Answers | Runner | Runs on |
|---|---|---|---|
| `Free checks` | compiles, tests pass, formatted | Linux | pull requests, manual dispatch |
| `Mac` | the app target compiles and the built bundle declares what it needs; on dispatch it also boots the app, screenshots it and queries the debug bridge | macOS | pull requests that change the app, package, project or config (through `Free checks`), manual dispatch |
| `Release` | signs and ships to TestFlight | macOS | a `v*.*.*` tag, manual dispatch |

A dispatch can ask one question: `gh workflow run mac.yml -f only=note,notes-offline` runs those
screens or sections of `Tooling/sim/sweep.sh`, and `-f script=<path>` sources a probe from the branch
after them. Either also skips the macOS-only tests.

`Mac` publishes the screenshots and the device log as artifacts, because every automated assertion
in that job can pass while the screen renders nothing.

## Releasing

Push a `v*.*.*` tag, or dispatch the workflow. The tag is the single source of truth for the
version; the build number is the CI run number. TestFlight builds expire after 90 days;
dispatching with `refresh_tag` rebuilds an existing release under a new build number to keep an
installed copy launching.

After each upload the `distribute` job attaches the build to the internal group and to the external
group named `Friends`, gives it its "What to Test" text and, for a build that has not been
reviewed yet, submits it to Beta App Review once the review contact is set (Apple reviews the first build of each version). The
external group and its public link, the beta description and the review contact and demo sign-in
are set up once per app with the App Store Connect API. A build that cannot reach external testers
fails the job rather than passing silently.
